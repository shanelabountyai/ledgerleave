# Phase 2 — Schema, triggers, writes, outbox, proofs (DRAFT, written at the Phase 1 gate; not started)

Drafted by the unattended session on 2026-10-25 as CLAUDE.md asks at a phase gate. **Nothing below is built.** The owner reviews this list, Phase 1 (PR #1) and the defaults in `docs/phase-1-plan.md` before Phase 2 begins. Order follows CLAUDE.md: schema and triggers → writes → outbox → proofs. The engines do not change; Phase 2 feeds them from tables instead of files and stores what they return.

Exit bar: `ledger:verify` against the **database** equals the oracle (198 rows, 0 diffs); replaying the fixture events twice writes nothing the second time; UPDATE/DELETE on the ledger and request-event tables is rejected by triggers; the outbox holds the expected `QUEUED` rows and nothing was sent.

- [ ] **2.1 Clone-owned schema.** `prisma/schema/ledgerleave.prisma` (never `core.prisma`): `Employee`, `OrgChange`, `Policy` (JSON column validated by `loadPolicyFile` on write, content hash), `PolicyAssignment`, `Holiday`, `Timesheet`, `Delegation`, `LedgerEntry` (L3 columns; `effective`/`posted` as `CHAR(10)` — **no `@db.Date`**, D-7), `LeaveRequest` (chain stored as submitted, D-20), `RequestEvent`, `RequestStep`. `businessId`/org scoping per the foundation's tenancy. *Acceptance:* `prisma validate`; a schema test asserts no `@db.Date` and no `balance`/`available` column anywhere (non-negotiable 1).
- [ ] **2.2 Append-only triggers.** Hand-written SQL in a clone migration: `BEFORE UPDATE OR DELETE` on `LedgerEntry`, `RequestEvent`, `RequestStep`-history raises; `seq`/`entry_id` assigned by the database in posting order. *Acceptance:* tamper tests — an UPDATE and a DELETE each fail with the trigger's message; INSERT succeeds.
- [ ] **2.3 Fixture import (inputs only).** `scripts/leave/import-fixtures.ts` loads the ten input files into the tables; never `ledger.csv`/`expected_*.csv`. Idempotent on the inputs (upsert by natural key). *Acceptance:* two runs, identical row counts and content hashes.
- [ ] **2.4 Replay-into-database.** `src/leave-db/replay.ts`: build a `World` from the tables, run `Simulation`, write every `Entry` and request state/event log. **Idempotent posting:** a second replay writes nothing (compare by `(employee, leave_type, kind, effective, posted, minutes, codes, ref)` natural key or by a replay hash). *Acceptance:* `ledger:verify --db` 198 rows 0 diffs; second run `0 inserted`.
- [ ] **2.5 Live writes through the engines.** Server actions: `submit` (chain frozen, A8 check, `RequestEvent` SUBMIT), `approve`/`deny` (S3 eligibility → void rows logged), `cancel` (reversals + A7 recompute in ONE transaction), `reassign` (HR only). Each writes the event row first and derives the rest by replaying that request through `applyEvent` — one code path for history and for live. *Acceptance:* GR-15 reproduced through the actions; a void approval leaves the ledger untouched.
- [ ] **2.6 Outbox (D-23).** Templates registered into the foundation's notifications module at runtime (Callboard pattern): `APPROVAL_REQUESTED` per kept step when it becomes current, `APPROVED`/`DENIED` to the requester; all `QUEUED`, never sent. *Acceptance:* replaying the fixtures yields the expected count of queued rows (derive the number from the 389 requests' kept steps and final states and state it); `EMAIL_ENABLED` stays off; no provider call in tests.
- [ ] **2.7 `ledger:verify` against the database.** Same `verifyLedger`, reading `LedgerEntry` rows. *Acceptance:* equals the oracle; a hand-edited row (via a superuser bypassing the trigger in a test transaction) is reported.
- [ ] **2.8 Nightly posting seam (P1, not built).** Document where a "post today's accruals" job would call the replay and prove it writes exactly the replay's rows. No cron work in Phase 2.
- [ ] **2.9 `docs/EVAL.md` Phase 2 section + CI.** CI applies all migrations to a throwaway Postgres, imports the fixtures, replays, verifies, runs the tamper tests. Numbers in `EVAL.md`.
