# Phase 2 — Schema, triggers, writes, outbox, proofs (built 2026-10-26, unattended; see `docs/EVAL.md` Phase 2 and D-35..D-41)

Drafted 2026-10-25 at the Phase 1 gate; built 2026-10-26 on the owner's "Go phase 2". Where the build departed from the draft wording the decision is named on the item. Order follows CLAUDE.md: schema and triggers → writes → outbox → proofs. The engines do not change; Phase 2 feeds them from tables instead of files and stores what they return.

Exit bar: `ledger:verify` against the **database** equals the oracle (198 rows, 0 diffs); replaying the fixture events twice writes nothing the second time; UPDATE/DELETE on the ledger and request-event tables is rejected by triggers; the outbox holds the expected `QUEUED` rows and nothing was sent. **Met**: 198 rows 0 diffs (`ledger:verify:db`), plus `leave:eval:db` 0 diffs on all three files; second replay 0/0/0/0 inserted; 10 tamper tests; 759 QUEUED, 0 sent — CI run 40321952682.

- [x] **2.1 Clone-owned schema.** `prisma/schema/ledgerleave.prisma` (never `core.prisma`): `Employee`, `OrgChange`, `Policy` (JSON column validated by `loadPolicyFile` on write, content hash), `PolicyAssignment`, `Holiday`, `Timesheet`, `Delegation`, `LedgerEntry` (L3 columns; `effective`/`posted` as `CHAR(10)` — **no `@db.Date`**, D-7), `LeaveRequest` (chain stored as submitted, D-20), `RequestEvent`, `RequestStep`. `businessId`/org scoping per the foundation's tenancy. *Built as* `PolicySet` (whole file) + `RequestCommand` (inputs) + `FrozenChain`/`RequestStep`/`RequestEvent` (derived) — D-36, D-37. *Acceptance:* `prisma validate`; a schema test asserts no `@db.Date` and no `balance`/`available` column anywhere (non-negotiable 1).
- [x] **2.2 Append-only triggers.** Hand-written SQL in a clone migration: `BEFORE UPDATE OR DELETE` on `LedgerEntry`, `RequestEvent`, `RequestStep`-history raises; `seq`/`entry_id` assigned by the database in posting order. *Acceptance:* tamper tests — an UPDATE and a DELETE each fail with the trigger's message; INSERT succeeds.
- [x] **2.3 Fixture import (inputs only).** `scripts/leave/import-fixtures.ts` loads the ten input files into the tables; never `ledger.csv`/`expected_*.csv`. Idempotent on the inputs (upsert by natural key). *Acceptance:* two runs, identical row counts and content hashes.
- [x] **2.4 Replay-into-database.** `src/leave-db/replay.ts`: build a `World` from the tables, run `Simulation`, write every `Entry` and request state/event log. **Idempotent posting:** a second replay writes nothing (compare by `(employee, leave_type, kind, effective, posted, minutes, codes, ref)` natural key or by a replay hash). *Acceptance:* `ledger:verify --db` 198 rows 0 diffs; second run `0 inserted`. *Built as* a prefix-checked replay with `ReplayDivergence` (D-38); `npm run leave:replay`.
- [x] **2.5 Live writes through the engines.** Server actions: `submit` (chain frozen, A8 check, `RequestEvent` SUBMIT), `approve`/`deny` (S3 eligibility → void rows logged), `cancel` (reversals + A7 recompute in ONE transaction), `reassign` (HR only). Each writes the event row first and derives the rest by replaying that request through `applyEvent` — one code path for history and for live. *Acceptance:* GR-15 reproduced through the actions; a void approval leaves the ledger untouched. *Built as* library functions, not server actions (D-39); the "replay that request" became "append the command, replay the day open" — one path, no per-request variant.
- [x] **2.6 Outbox (D-23).** Templates registered into the foundation's notifications module at runtime (Callboard pattern): `APPROVAL_REQUESTED` per kept step when it becomes current, `APPROVED`/`DENIED` to the requester; all `QUEUED`, never sent. *Acceptance:* replaying the fixtures yields the expected count of queued rows (derive the number from the 389 requests' kept steps and final states and state it); `EMAIL_ENABLED` stays off; no provider call in tests. *Number:* **759** (382 APPROVAL_REQUESTED · 322 APPROVED · 55 DENIED), counted from the oracle's log lines; the cron drain is unwired (D-40).
- [x] **2.7 `ledger:verify` against the database.** Same `verifyLedger`, reading `LedgerEntry` rows. *Acceptance:* equals the oracle; a hand-edited row (via a superuser bypassing the trigger in a test transaction) is reported.
- [x] **2.8 Nightly posting seam (P1, not built).** Document where a "post today's accruals" job would call the replay and prove it writes exactly the replay's rows. No cron work in Phase 2. *Documented* in `src/app/cron-jobs.ts`; the "exactly the replay's rows" proof is the prefix-growth test (`replay.test.ts`); the calendar-day source for "yesterday" is O-13.
- [x] **2.9 `docs/EVAL.md` Phase 2 section + CI.** CI applies all migrations to a throwaway Postgres, imports the fixtures, replays, verifies, runs the tamper tests. Numbers in `EVAL.md`.
