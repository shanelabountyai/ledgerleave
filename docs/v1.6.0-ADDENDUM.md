## 2. Row-level security (opt-in, D-23)

With `RLS_MODE=enforce`, Postgres refuses a cross-org row even when application code forgets `inOrg(ctx)`. App-only isolation (INV-02/03/04) stays in force; RLS is a second, independent wall.

**Request path, enforce mode**

1. `requireOrg(slug)` resolves the membership as today and returns `OrgCtx`.
2. Every org-scoped database call goes through `withOrg(ctx, fn)` in `src/core/db/rls.ts`: it opens a Prisma interactive transaction, runs `SELECT set_config('app.org_id', $1, true)` (the `true` makes it transaction-local), then runs `fn(tx)`.
3. Policies on every org-owned table compare `"orgId" = current_setting('app.org_id', true)::uuid`. A missing setting yields NULL and matches no row, so an unscoped call sees nothing rather than everything.
4. The transaction ends and the setting is gone with it. Neon's pooler runs in transaction mode, so `set_config` with `is_local = true` never leaks to the next borrower of the connection. `SET` without `LOCAL` is forbidden (INV-31 greps for it).

**Two database roles.** Migrations and cross-org work run as the owner role, which has `BYPASSRLS`. The app connects as `app_rw`, which does not. The cross-org paths are the ones that run before an org is known or across orgs: sign-in, invite redemption, `/onboarding`, the Stripe and SSO webhooks, cron, and `seed:demo`. Each is listed in `src/core/db/cross-org.ts` and goes through `asSystem(fn)`, which uses a second Prisma client on `DATABASE_URL_SYSTEM`. The list is closed: a new cross-org call outside it fails INV-32.

**Policies are generated, not hand-written.** `npm run rls:policies` reads `prisma/schema/*.prisma`, finds every model with an `orgId` column, and writes one migration with `ALTER TABLE … ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, and one `FOR ALL` policy per table. The template runs it over core tables in v1.6.0's own migration; a clone runs it once for its tables and commits the result. A model with `orgId` but no policy fails INV-30 in enforce mode.

**Tables without `orgId`** (`User`, `Session`, `LoginToken`, `RecoveryCode`, `RateLimit`, `AuditEvent`) are not org-owned and get no policy. `AuditEvent` keeps its append-only trigger (INV-19) and carries `orgId` for the viewer's filter, so it gets a read-only policy: insert is unrestricted, select is scoped.

**Cost.** One extra round trip per request for `set_config`, inside a transaction the request already needed for most writes. Reads that were single statements become two. Measured in the template's e2e on Neon before the tag; the number goes in `CHANGELOG.md`.

**Off mode** (`RLS_MODE` unset): `withOrg` still runs `fn` inside a transaction with `set_config`, but the policies are not enabled on the tables, so behaviour is identical to v1.4.1 and the code path is exercised in every clone. Turning on enforce mode is then a migration, not a code change.

**What this does not cover.** RLS protects rows. It does not stop a query that is scoped correctly but returns too many columns, and it does not replace `toPublicX()` projections (INV-08). It also cannot protect a clone that connects as the owner role; INV-33 checks the runtime URL's role.

**As built in M9 (2026-11-05): where the build differs from the text above.**

1. **Off mode is the role, not the migration** (kickoff M9 item 4). The generated migration always enables and forces RLS. Off mode
   means the app connects as the owner, which has `BYPASSRLS` (local superuser, Neon `neondb_owner`: both measured in S4b). Turning
   enforce on is a role and env change, not a migration. `RLS_MODE=enforce` requires `DATABASE_URL_SYSTEM`, and INV-29/30/33 run only then.
2. **Policies use `nullif(current_setting('app.org_id', true), '')::uuid`.** Once a transaction-local setting has been used on a
   connection, it reads `''`, not NULL, and `''::uuid` throws (S4a). Without `nullif`, an unscoped query on a reused pooled
   connection errors instead of returning no rows.
3. **A nullable `orgId` means an append-style table** (`AuditEvent`, `Outbox`): INSERT is open, and SELECT, UPDATE and DELETE are
   scoped. Writers use `createMany`, not `create`, because `INSERT … RETURNING` must also pass the SELECT policy.
4. **`requireOrg` reads `Org` by slug first** (no policy on `Org`), then the membership inside `withOrg`. `createOrg` chooses the org
   id itself, so the owner membership is written inside the new org's scope. Neither needs `asSystem`.
5. **The cross-org list is longer than §2's.** These were added, each found by reading every call site or by the enforce leg:
   share-link read by token, account deletion, turning TOTP off (owner/admin anywhere), email change (revokes invites to the old
   address in every org; INV-06 failed in the enforce leg until it moved), and the demo user list. `src/core/db/cross-org.ts` gives
   each one's reason.
6. **Cost is four round trips, not two:** BEGIN, `set_config`, the query, COMMIT. S4c numbers are in `CHANGELOG.md`.
   **D-31 (owner, 2026-11-05): off mode skips it.** With `RLS_MODE` unset, `withOrg` runs no `set_config`; reads marked
   `{ atomic: false }` run on the plain client, and writes keep the transaction they had before v1.6.0. A clone that keeps RLS off
   pays nothing. The enforce path is tested by the CI enforce leg on every push, not by off mode. Replaces kickoff M9 item 4's
   "in both modes withOrg sets the setting".
7. **Local app role is per project** (`<name>_app_rw`), since Postgres roles are shared by every database on the server. It needs
   sequence grants too (`AuditEvent.id` is an autoincrement). `db:setup` writes it as `DATABASE_URL_APP_RW` and keeps the owner as
   `DATABASE_URL`: with RLS off nothing sets an org, so a NOBYPASSRLS login would see no org rows. An off-mode test fails when the
   runtime role cannot bypass RLS (the mirror of INV-33).

## 3. SSO module (OIDC, D-24 to D-26)

An org owner connects the org to its own identity provider. Members of that org then sign in through the provider instead of a magic link, and the org can require it.

**Tables** (`prisma/schema/sso.prisma`, back-relation line in `core.prisma` marked `// sso`)

| Table | Columns that matter | Notes |
|---|---|---|
| `SsoConnection` | `orgId` (unique), `issuer`, `clientId`, `clientSecretSealed`, `discoveryUrl`, `defaultRole` (`member`), `allowedDomains` (text[]; JIT only when non-empty and the verified email domain / `hd` matches, §10.2–3), `required` (false), `enabledAt`, `disabledAt` | One per org in v1.6.0. Secret sealed with `sealSecret(secret, 'sso')`, the TOTP pattern (INV-25 extended). |
| `SsoDomain` | `orgId`, `domain`, `verificationToken` (hash), `verifiedAt` | A DNS TXT record `_foundation-sso.<domain>` proves ownership. Unverified domains never match a sign-in. A domain belongs to at most one org. |
| `SsoState` | `hash`, `orgId`, `nonce`, `codeVerifier`, `returnTo`, `expiresAt` | Authorization-code + PKCE state, 10-minute TTL, single use, hashed (INV-07). |
| `User.ssoSubjects` | `(issuer, subject) → userId` | A provider's stable subject id. Email is matched once at first sign-in, then the subject is the key, so an email change at the provider cannot hijack an account. |

**Sign-in flow**

1. `/login` gains one field: email. If the email's domain matches a verified `SsoDomain` whose connection is enabled, the user is redirected to `/login/sso/start?org=<slug>`. Otherwise the magic-link flow runs unchanged. The response shape is identical either way until the redirect (D-10, no probing).
2. `start` writes an `SsoState` row and redirects to the provider's authorization endpoint with PKCE, `nonce`, and `login_hint`.
3. `/login/sso/callback` is a route handler (same reason as `/login/redeem`: INV-01 keeps no exemptions). It spends the state row, exchanges the code, validates the ID token (`iss`, `aud`, `nonce`, `exp`, signature from the discovery document's JWKS), and requires `email_verified = true`.
4. The token's `email` domain must be a verified domain of that org, or the sign-in fails closed with the same 404 as any other bad link.
5. Just-in-time membership (§10.3, tightened): a known subject signs in. An unknown subject whose email matches an existing user links to it (the provider has verified the email, step 3); otherwise a new `User` is created. If the user has no membership in the org, one is created with `defaultRole` **only** when the email's domain is in the connection's `allowedDomains` (and, for Google, `hd` matches it). Otherwise the sign-in needs a pending invite for that email, or it fails closed. Owners are never created this way (INV-28, INV-38).
6. A session is written with `authAt = now`. It satisfies the owner/admin MFA rule (INV-22) **only** when the ID token's `amr` includes `mfa` (§10.2, tightened); then `mfaAt = now` too. Without it, an owner or admin who signs in by SSO still completes TOTP, because many providers do not enforce MFA.

**As built in M10 (2026-11-05): where the build differs from the text above.**

1. **The seam is a registry**, `registerSsoHooks(hooks)` in `src/core/auth/sso-hook.ts` with `resolve(email)` and `refusesLink(userId)`. ESLint forbids `src/core` importing `src/app` or `src/modules` (spec §4), so `src/app/modules.ts` registers and the two sign-in routes (`/login/request`, `/login/redeem`) import it for that side effect. An INV-36 test fails if either route loses the import.
2. **MFA scope:** a provider's `amr: mfa` is stored as `Session.mfaOrgId` and counts in that org only. A TOTP-enrolled user still does their own TOTP step after SSO.
3. **ID token signature:** openid-client skips the JWKS check for a token fetched from the token endpoint (OIDC Core 3.1.3.7). The module turns it on (`enableNonRepudiationChecks`); INV-37's tampered-signature case went red without it.
4. **Google `hd`** is checked on every sign-in through a shared issuer, not only for JIT.
5. **A pending invite is not auto-accepted.** The user gets a session and accepts it on `/onboarding`, the same path as a magic-link sign-in.
6. **State is cookie-bound.** The state value is also a `__Host-sso-state` cookie, so a callback only completes in the browser that started it (login CSRF).
7. **A recycled address fails closed.** An unknown subject is not linked to an existing user who already has a different subject at the same issuer.
8. **Dropped columns:** `discoveryUrl` (derived from the issuer), `SsoState.returnTo` (always `/onboarding`), `SsoDomain.verificationToken` (the TXT value is an HMAC of org and domain under `AUTH_SECRET`, so nothing is stored). `disabledAt` is `enabledAt = null`. Added: `requiredAt`, `requiredById` (the 24-hour exemption) and `SsoState.test`.
9. **Domain uniqueness** is enforced when a domain is verified, not by a unique column, so an org cannot squat a domain it has not proved.
10. **Turning SSO off also drops "required"**, so a broken provider can always be backed out of. Required needs an enabled connection.
11. **`src/app/api/webhooks/sso/**` is not created:** IdP-initiated sign-in is out of scope.

**SSO-required.** With `required = true`, a magic link for a member of that org is refused at `requestLink` and at `redeemLink` (the link can still be requested without probing; it simply does not work). The owner who turned it on is exempt for 24 hours, so a misconfiguration cannot lock everyone out. Demo users are never SSO users.

**Core seam.** Core gets `src/core/auth/sso-hook.ts`: `registerSsoResolver(fn)` and `resolveSso(email)`. With the module absent the resolver returns null and `/login` behaves as v1.4.1. The module registers its resolver from `src/app/modules.ts` (clone-owned, one marked line per module, created in this release).

**Settings page** `/o/[org]/settings/sso` (template-owned, `org.update` plus owner role): connection form, domain list with verification status and the TXT record to add, a *Test sign-in* button that runs the flow in a popup against the saved connection without writing a session, and the *Require SSO* switch. Every change is audited.

**Test providers** (D-26): a Google Workspace connection for `labintelligence.co` and an Okta Integrator Free org. `seed:demo` creates two demo orgs with the two connections pre-filled from `.env.local`, secrets never printed. The e2e suite mocks the provider with a local OIDC server (`tests/helpers/oidc-mock.ts`), so CI needs no provider account; the two real providers are checked by hand before the tag and the result recorded in `CHANGELOG.md`.

**Out of scope for v1.6.0:** SAML, SCIM provisioning and deprovisioning, more than one connection per org, group-to-role mapping, IdP-initiated sign-in.

## 4. Audit-log viewer (F-01) and security page (F-02)

Both are UI over rows and flows that already exist. They close the two oldest `BACKLOG.md` items and give Earmark its admin story.

**Audit-log viewer** `/o/[org]/settings/audit`, permission `audit.read` (owner and admin, already in `grants`). A table of `AuditEvent` rows for the org, newest first, filtered by actor, action and date range, cursor-paginated at 50. Each row shows actor, action, target type and id, and the `meta` JSON folded. No edit affordance exists: the trigger refuses UPDATE and DELETE (INV-19) and the page has no action for either. A *Download CSV* button streams the same filter through the data-export path (§5), so there is one exporter, not two.

**Org security page** `/o/[org]/settings/security` (owner and admin): members with and without TOTP enrolled, each member's last sign-in and sign-in method (link or SSO), the org's SSO status when the module is present (marked `{/* sso */}`), and the *Require SSO* switch moved here from the SSO page if both exist. No action on this page changes another user's credentials; it only shows and links.

**Account security page** `/account/security` gains a sessions list: each session's created time, last seen, rough location from IP (country only, never stored beyond the row), and a *Sign out* per row plus the existing *Sign out everywhere*. Revoking one session deletes its row; the rest hold (INV-05 unchanged). The current session is marked and cannot be revoked from the list.

All three pages are template-owned security routes (D-12): thin, with the queries in `src/core/audit.ts` and `src/core/auth/sessions.ts`.

## 5. Per-org data export

An owner downloads everything the org owns as one archive. This is tenant offboarding and the usual enterprise procurement question, and it was "later, not v1" in spec §9.

- **Trigger:** `/o/[org]/settings/danger`, owner only, fresh `authAt` (INV-26 extended), one export at a time per org, rate-limited to one per hour.
- **Shape:** a zip of JSON Lines, one file per table, plus `manifest.json` (org, tables, row counts, schema version, `FOUNDATION_VERSION`, sha256 per file). Core tables are always included: `Org`, `Membership` (with user email and name), `Invite`, `ShareLink`, `AuditEvent`, `Project`, and each present module's tables. A clone adds its own tables in `src/app/export-hooks.ts` with `exportTable(name, (ctx) => query)`.
- **Scope:** every query runs through `withOrg(ctx, …)`, so in enforce mode RLS bounds the export too. Secrets are never exported: sealed columns, token hashes and recovery codes are dropped by an allowlist per table (INV-34 checks the output for anything token-shaped).
- **Delivery:** the archive is built by cron (`export.run` job in `cron-jobs.ts`'s template half), stored at a Vercel Blob URL that expires in 24 hours, and the owner is emailed a link to a `/o/[org]/settings/danger/export/[id]` page that requires sign-in and owner role to download. The URL itself is never emailed.
- **Audit:** `export.requested` and `export.downloaded` events, with the manifest's sha256.
- **Size guard:** exports over 500 MB stop and tell the owner to contact support. No clone is near that; it exists so a runaway query cannot fill the build budget.

**As built in M11 (2026-11-05): where the build differs from §4 and §5.**

1. **The archive lives in Postgres, not Vercel Blob** (owner decision, 2026-11-05): table `OrgExport` holds the zip as `bytea` for 24 hours, then `/api/cron` deletes the row. No new dependency or secret, and INV-34 checks real bytes locally and in CI. Ceiling: fine at demo sizes; move to object storage if a clone's exports reach a few MB.
2. **Built right after the request, cron as backstop.** The action schedules the build with Next's `after()`; `/api/cron` (daily) builds any export still waiting, or one whose build died over an hour ago. A cron-only build would make an owner wait up to a day.
3. **The export job sits in `/api/cron/route.ts`, beside the rate-limit sweep,** not in `cron-jobs.ts`, which is clone-owned and would conflict on every merge.
4. **Clone tables are a list, not calls:** `src/app/export-hooks.ts` exports `exportTables: ExportTable[]` (`{ name, rows: (tx, orgId) => query }`), and module tables come from marked lines in `src/app/modules.ts`. Core never imports `src/app`, so the app passes the list to `buildExport` and `runExports`. **INV-34 also checks coverage, like INV-30 for policies:** every model with an `orgId` column must be exported or listed with a reason in `NOT_EXPORTED` (core: `OrgExport`, `SsoState`) or the clone's `exportSkipped`, so a clone table cannot silently drop out of every export.
5. **Zip entries are stored, not deflated,** written with `node:zlib`'s `crc32` (no dependency). The archive is the JSON Lines byte for byte, so INV-34 scans it directly; the test unpacks it with the system `unzip` so a reader other than ours checks it.
6. **Excluded columns** (the allowlist, INV-34): `Invite.tokenHash`, `ShareLink.tokenHash`, `Outbox.data` (an invite email's data holds its link), `SsoConnection.clientSecretSealed`, and all of `SsoState`. Users' TOTP and recovery codes never come in: only `Membership` with the user's email and name.
7. **Audit events:** `export.requested`, `export.ready` (actor null, with the manifest's sha256) and `export.downloaded` (with the sha256). `export.requested` cannot carry the sha256 because nothing is built yet.
8. **Sign-in data is new columns:** `Session.method`, `Session.lastSeenAt` (written at most every 5 minutes) and `Session.country` (from Vercel's `x-vercel-ip-country` header; the IP is never read); `User.lastSignInAt` and `User.lastSignInMethod`, because sessions are deleted on sign-out and the org security page needs the last one.
9. **The audit CSV** is a route (`/o/[org]/settings/audit/csv`) over the same `auditEvents` query the export uses. Cells starting with `= + - @` are prefixed with `'` so a spreadsheet does not run them.
10. **The Require SSO switch moved to the Security page** as `src/app/o/[org]/settings/sso/security-panel.tsx` (it goes with the module); the SSO page now links to it. Owner only, as before.
11. **Nav:** owners and admins see *Audit log* and *Security*; *Delete org* is now *Export or delete*.

## 6. AI spend guards

A model call cannot exceed what the org has agreed to pay for. Footnote, Triage, the Claims Intake module and the Agentic track all call models today with no shared ceiling; the Use-Case Studio spend guard is the reference (spec §11).

- **Table `AiUsage`** (core, `orgId`, policy-scoped): `provider`, `model`, `inputTokens`, `outputTokens`, `costMicros` (integer micro-dollars, no floats), `feature` (a clone-chosen label), `actorId`, `createdAt`. Append-only by convention, not trigger: it is a ledger, and summing it is how a budget is checked.
- **Table `AiBudget`** (one row per org, created on first spend with the template default): `monthlyCapMicros` (default $25.00), `hardStop` (true), `alertAtPct` (80), `pausedAt`.
- **`withBudget(ctx, feature, fn)`** in `src/core/ai/budget.ts`: sums this calendar month's `costMicros` for the org; refuses with `BudgetExceeded` if the cap is reached and `hardStop` is on, or if `pausedAt` is set; otherwise runs `fn`, which must return `{ usage }`; writes the `AiUsage` row from it. Prices per model live in `src/core/ai/prices.ts` as data with an as-of date, so a price change is one commit.
- **Alerts:** crossing `alertAtPct` sends one email per month to the org's owners through the existing transport. Reaching the cap sends one more. Both audited.
- **Owner controls:** `/o/[org]/settings/billing` (when the billing module exists) or `/o/[org]/settings/security` (when it does not) gains a card: this month's spend, the cap, a pause switch. Raising the cap needs `billing.manage`.
- **Operator kill switch:** `AI_ENABLED=0` makes every `withBudget` call refuse, the same shape as `EMAIL_ENABLED=0` (INV-11 pattern).
- **Not covered:** this guards cost, not content. Prompt-injection and output handling stay with each clone.

**As built in M12 (2026-11-05): where the build differs from the bullets above.**

1. **Hard cap by reservation** (owner decision, 2026-11-05). Checking the sum before a call and writing the cost after it lets calls in flight, or one large call, pass the cap. So the signature is `withBudget(ctx, feature, maxCostMicros, fn)`: the caller passes the call's worst case (known input tokens plus `max_tokens` of output, priced with `costMicros`). Under `SELECT … FOR UPDATE` on the org's `AiBudget` row, the call is refused when month spend + live holds + this estimate would pass the cap; otherwise the estimate goes in a new table **`AiHold`**, `fn` runs, and the hold is swapped for the `AiUsage` row at the billed cost. A throwing `fn` releases its hold and writes no usage. A crashed process's hold stops counting after 15 minutes (`HOLD_MS`) and the next check deletes it. The cap is exact only if the estimate is a true upper bound; an under-estimate is still recorded at its real cost.
2. **`AiBudget` gains `alertedAt` and `cappedAt`.** The one-email-a-month rule is a conditional update that claims the month, so two calls crossing 80% together send one email.
3. **The card lives on `/o/[org]/settings/security` only**, billing module or not: the billing page is module-owned and removable, and one place is simpler. Owners and admins see it.
4. **Every change (cap, pause, resume) needs `billing.manage`**, not only raising the cap: stricter than the bullet, and owner-only today. A demo session cannot change either (the shared $1.00 cap must stay).
5. **`BudgetExceeded` extends `Refused`**, so an `orgAction` shows its message. `AI_ENABLED=0`, a pause and the cap all refuse with it, each with its own message.
6. **Pricing:** a model's long-prompt tier is in the table (Haiku 5.5 above 100k input tokens bills the whole call at 5x), so a long call is not recorded below its real cost. All input is priced at the base input rate: cache reads are over-counted (safe for a cap) and a cache write's premium is under-counted, which matters only to a clone that uses prompt caching with a hard cap. A model missing from `prices.ts` throws instead of reading as free. Prices come from footnote's `config/prices.json`, read from Anthropic's pricing page on 2026-10-19.
7. **`AiUsage.actorId` is nullable**, for calls no user made (cron). `AiUsage` and `AiBudget` are in the export; `AiHold` is not (in-flight, minutes long).

## 7. API keys + outbound webhooks module (`apikeys`, D-28)

A port of Bookable's W- track (items W-000 to W-013 are done there) into a per-org module. What changes is the tenant: every key, event and endpoint belongs to an org, and every lookup goes through `inOrg` and, in enforce mode, RLS.

**Kept from Bookable, unchanged in design**

- Keys: one per integration, sha256-hashed with a visible prefix, shown once, scoped, revocable, per-key rate limits (120 reads and 20 writes per minute by default, `Retry-After` on refusal).
- Idempotent writes: `POST` without an `Idempotency-Key` is refused; a replay returns the stored response; a reused key with a different body is rejected.
- Versioning by path (`/api/v1`), cursor pagination capped at 100, problem+json errors with one code vocabulary.
- Webhooks from an append-only event log with a per-org sequence number; HMAC-SHA256 over timestamp + body; receivers reject stale timestamps; secrets rotate with a 24-hour overlap.
- Delivery: inline dispatch after the write, hourly sweep for retries, six-attempt backoff, then dead-letter; ten consecutive failures pause an endpoint, a 410 disables it; a snapshot per delivery so replays show what was true then; a catch-up endpoint by sequence number.

**Changed for the foundation**

| Bookable | Foundation module |
|---|---|
| Key → one business | `ApiKey.orgId`; `requireApiKey(req)` returns an `OrgCtx` with `role = 'integration'` and the key's scopes, so `orgAction` bodies are reusable from API routes |
| Scopes `read`, `write`, `prices`, `contacts` | Scopes are declared by the clone in `src/app/api-scopes.ts`; the module ships `read` and `write` |
| Event types fixed to appointments | A clone names its events in `src/app/event-types.ts` and calls `emit(ctx, type, payload)` from its actions; core's `audit()` and `emit()` share one transaction so an audited change cannot miss its event |
| Sweep in Bookable's cron | The sweep is a template line in `/api/cron`, marked `// apikeys` |
| Settings in the desk | `/o/[org]/settings/apikeys`: keys, endpoints, delivery log with replay, all behind `members.manage` plus a new `apikeys.manage` permission granted to owner and admin |

**Pulseboard** keeps working: its `/ingest` write key (clone D-003) is migrated to an `ApiKey` row with scope `ingest` in its own v1.6.0 upgrade PR, and the hand-rolled check is deleted. That PR is the module's first real test outside the template.

**Out of scope:** OAuth for third parties, a developer portal, inbound webhooks, exactly-once delivery.

**As built in M13 (2026-11-05): where the build differs from the text above.**

1. **The event log is core, the delivery is the module.** `OrgEvent` (core table) and `emit(ctx, type, payload, tx)` (`src/core/events.ts`) live in core, so a clone's actions can call `emit` whether or not it keeps `apikeys`; core never imports a module, and a registration seam would lose events silently in any route that forgot to import `modules.ts`. Without the module the log is still written and exported, and nothing sends it. `tx` is required (not defaulted like `audit`'s), so an event cannot be written outside its change's transaction.
2. **`seq` is handed out at commit** by a deferred constraint trigger that bumps a new `Org.eventSeq` column (Bookable W-D18, with the counter on `Org` instead of a separate table). Commit order, gapless, and no writer takes part. The trigger is `SECURITY DEFINER`, so it numbers events under RLS enforce whatever the setting.
3. **Delivery timing.** An API write sends its webhooks right after the response (`after()`). Retries after a failure and events emitted from page actions go out on `/api/cron`, which the template schedules **daily** (`vercel.json`), not hourly: a retry due in a minute can wait up to a day, and six attempts can stretch over about six days before a delivery is dead. Kept daily on purpose (cost: every run wakes the database; Bookable runs the same inline + daily). A clone that needs prompt retries sets its cron to hourly.
4. **`requireApiKey` and the key lookup live in the module**, not core: they need the module's `ApiKey` table. Core's part is `hashToken`, unchanged. The context is an `ApiCtx` (`orgId`, `keyId`, `scopes`, `role: 'integration'`, `userId: null`), not an `OrgCtx`: there is no session to fake. `inOrg` and `withOrg` take any `{ orgId }`, so an action's body that only needs those is reusable; audit lines from the API carry `data.apiKeyId`.
5. **Scopes carry their rate limit.** `src/app/api-scopes.ts` maps each scope to its per-key, per-minute limit (`read` 120, `write` 20); a clone adds e.g. `ingest` with its own. `requireApiKey(req, scope)` is exported for a clone's own non-`/api/v1` routes (Pulseboard's `/ingest`).
6. **No per-delivery snapshot table.** The emitted payload is stored once on the event and is the snapshot every delivery, replay and `GET /api/v1/events` sends. Bookable needed `EventSnapshot` because its log payload was not the public view; here the clone writes the public view at `emit`.
7. **Dedupe is an explicit key.** `emit(…, { key })` with a key already used in that org writes nothing; without a key every emit is a new event. Fan-out is unique on (endpoint, event), so two sweeps can never send one event twice (INV-41).
8. **Signing secrets are sealed** (`sealSecret(secret, 'webhook')`), not stored plain as in Bookable: the sender must read them back, so they cannot be hashed. The header is `Webhook-Signature: t=<unix>,v1=<hex>`; `verifySignature` in the module is the receiver half (±300 s).
9. **The outbound half of INV-12 lives in the INV-41 file**, not in `inv-12-webhooks.test.ts`: that file belongs to the billing module and would be deleted with it.
10. **`/api/v1/projects` lists by id**, a keyset that is stable under writes; a `createdAt` cursor at millisecond precision would skip rows that share a millisecond.
11. **Replay is per delivery.** Bookable's "replay from seq" button is left out; a receiver catches up with `GET /api/v1/events?since=`.
12. **Small core changes:** `apikeys.manage` (owner, admin); a form field named with `[]` (`scopes[]`) reaches an action as an array, for checkbox groups; any other name posted twice keeps its last value as before, because clones put a hidden "0" before a checkbox of the same name (an earlier draft of M13 turned every repeated name into an array, which would have broken those forms); the rate-limit `Limit` type accepts any `{ limit, windowMs }`.
13. **A key dies with its creator's membership** (owner decision, 2026-11-05). Bookable's keys belong to the business and outlive the person who made them; here removing a member, a member leaving, or deleting an account revokes every key that person created, in the same transaction, audited as `apikey.revoked_with_member`. Same reasoning as K6 for share links: a copied credential must not outlive the access of the person who copied it. Cost: an integration an admin set up stops when they leave, and an owner issues a new key. Mechanism: a clone-owned hook `onMembershipEnded(tx, orgId, userId)` in `src/app/org-hooks.ts`, a **required** argument of core's `removeMember` and `deleteAccount` (so no caller can skip it); its `// apikeys` line goes with the module. INV-40 covers removal, leaving and account deletion.
14. **The CI enforce leg is opt-in per clone** (owner decision, 2026-11-05; found by the Pulseboard proof, whose plain-`db` queries failed it). The template runs both legs; a clone runs `enforce` only once it sets the GitHub repo variable `RLS_ENFORCE=1`, so merging v1.6.0 cannot turn a clone red (D-23, §1). INV-29 seeds a clone's own org tables through `tests/fixtures/app.ts` `seedApp`, the fixture the action harness already uses, so an opted-in clone's tables are covered too.

## 10. Open decisions (approved by owner 2026-11-04: 1 and 4 to 7 as written, with small additions to 1 and 4; 2 and 3 tightened)

1. **Second Prisma client for `asSystem`, or one client with role switching (`SET LOCAL ROLE`)?** Default: **two clients, two URLs.** Simpler to reason about and INV-33 can check the runtime URL directly. Cost: one more env var (`DATABASE_URL_SYSTEM`) and one more pool. **Approved 2026-11-04**, with the local pool cap split between the two clients (e.g. `connection_limit=8` app, `2` system) so a project still opens at most 10.
2. **Does an SSO session satisfy the owner/admin MFA rule (INV-22)?** **Approved 2026-11-04, tightened:** only when the ID token's `amr` claim includes `mfa` (or the provider's documented equivalent). Otherwise an owner or admin signing in by SSO still completes TOTP. Reason: many providers do not enforce MFA (a Google account without 2-Step Verification passes), so "the provider is the second factor" is not true by default. INV-22 gets a case for each path.
3. **JIT membership on first SSO sign-in, or invite-only?** **Approved 2026-11-04, tightened:** JIT with `defaultRole = member` **only** when `email_verified` is true **and** the email's domain is in the connection's `allowedDomains` (for Google Workspace, the `hd` claim must also match). Otherwise the sign-in needs a pending invite. `SsoConnection` gains `allowedDomains` (required and non-empty to turn JIT on). Reason: Google uses one shared issuer for every Google account, so issuer-only JIT would let any Gmail user join. Clones where membership is a billing event can still set invite-only. Invariants INV-35 to 38 cover a wrong domain, unverified email and a missing or mismatched `hd`.
4. **Export delivery via Vercel Blob or direct stream?** Default: **Blob with a 24-hour expiry**, because a 100 MB stream from a serverless function times out. Needs `BLOB_READ_WRITE_TOKEN`, optional; without it the export is refused with a clear message. **Approved 2026-11-04**, plus: each download URL is unguessable, single-use and checked against the requesting owner (one test).
5. **AI budget default cap.** Default: **$25.00 per org per month**, hard stop on. Demo orgs seed at $1.00 so the refusal path is visible in a demo. **Approved 2026-11-04.**
6. **Does the `apikeys` module also cover inbound (third-party → app) webhooks generically?** Default: **no**; Stripe and SSO callbacks stay as they are. Revisit when a clone needs a second inbound provider. **Approved 2026-11-04.**
7. **Where do new permissions go?** Default: `apikeys.manage` and `export.run` are added to `Permission` in core (owner and admin; `export.run` owner only). The grants table grows; no role changes. **Approved 2026-11-04.**

**Spikes before code (M9 start):** Prisma 7 interactive transaction + `set_config` through the Neon pooler, measured; `prisma migrate` running as the owner role while the app runs as `app_rw` on the same Neon branch; `openid-client` v6 against Google's discovery document in a Next 16 route handler.
